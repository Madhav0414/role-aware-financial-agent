# Architecture

The shape of the system, not its implementation detail. For the execution path
through a single question see [`FLOW.md`](FLOW.md); for why each choice was made
see [`DECISIONS.md`](DECISIONS.md).

---

## The organising principle

> **Deterministic core, LLM at the edge.**

Every figure, every access decision and every refusal is produced by ordinary
Python. The language model does two things only: it helps interpret how a
question is phrased, and it words the final answer.

Three consequences follow, and they are the reason for the choice:

1. **Testable.** An access decision is a pure function of a role and a plan, so
   it can be asserted rather than sampled.
2. **Reproducible.** The same question returns the same figures every time. A
   regulator, or an evaluator, cannot audit a number that varies per run.
3. **Runs with no key.** The model is optional. Half the assignment's marks are
   for running end to end, and that should not depend on someone else's billing.

## Layers

```
   data/raw/                    PDF + XLSX, committed
       │
       ▼
   ┌────────────┐   deterministic tagging from config/sources.yaml
   │  INGEST    │   → Fact (typed figure)   → Chunk (passage)
   └─────┬──────┘
         ▼
   ┌───────────────┐  precomputed once, regenerable in 3 seconds
   │ UNDERSTANDING │  facts.db · bm25.json · summaries/ · metric_tags.json
   └─────┬─────────┘
         ▼
   ┌──────────────────────────────────┐
   │  ACCESS GATE   +  DERIVATION     │  ← the only path to data
   │                   GUARD          │
   └─────┬────────────────────────────┘
         ▼
   ┌────────────┐   query_metrics · search_filings · get_schema · list_sources
   │ AGENT      │   RBAC lives INSIDE each tool
   └─────┬──────┘
         ▼
   ┌────────────┐        ┌──────────────┐
   │ CLI / WEB  │ ─────► │  FEEDBACK    │──┐
   └────────────┘  👍👎  └──────────────┘  │
         ▲                                  │
         └──────────────────────────────────┘
                  re-ranks the NEXT answer
```

Each layer is independently testable, and the dependency arrows only ever point
downward — `src/access/` imports nothing from `src/ingest/` or
`src/understanding/`.

## 1. Ingest

**`src/ingest/`** — turns two file formats into two typed records.

| Module | Responsibility |
|---|---|
| `pdf_loader.py` | PyMuPDF → `(page_number, text)`, 1-based for citations |
| `excel_loader.py` | Both workbook layouts → `Fact` |
| `tagger.py` | Heading → sensitivity `Tag`, declaratively |
| `chunker.py` | Pages → `Chunk`, carrying section state across pages |

Two shapes of spreadsheet exist in the corpus — SEC-published workbooks split
the header across two rows with the duration in merged cells, while the rebuilt
ones combine them. One parser handles both by scanning the first rows as a
header *block* and carrying durations rightwards.

**Tagging is declarative and deterministic.** Every rule lives in
`config/sources.yaml` and no model is consulted. An access decision that depends
on an LLM's classification is not an access control; it is a suggestion.

Two structural safeguards:

- **Document type constrains the tag space.** A proxy statement can only ever
  produce `governance`, `hr.compensation` or `narrative.risk`, whatever its
  headings say. Heading matching is a heuristic and will sometimes be wrong, so
  the design bounds the blast radius rather than chasing a perfect heuristic.
- **Category headers scope the rows beneath them.** XBRL renderings nest
  breakdowns — a row reading `iPhone` with no figures, then `Net sales` carrying
  209,586. Flattened, `net_sales` resolved to twenty different values.

## 2. Understanding

**`src/understanding/`** — the derived artifacts, regenerated by
`scripts/build_understanding.py`.

| Artifact | Contents | Answers |
|---|---|---|
| `facts.db` | 4,684 typed figures | exact numeric questions, by SQL |
| `index/bm25.json` | 741 narrative chunks | "what does management say…" |
| `summaries/*.json` | per-document metadata | which document to look in |
| `metric_tags.json` | metric → every tag it appears under | what a plan must declare |
| `schema_notes.md` | generated description | human orientation |

**What is precomputed, and why:** anything whose failure would be *silent* —
metric extraction, tagging, the index. A mis-parsed figure discovered at query
time is indistinguishable from a correct one, so it is better produced once,
visibly, where it can be checked. Anything cheap and query-dependent —
aggregation, ranking, phrasing — is computed live.

**Two retrieval paths, deliberately.** Vector and lexical search are both weak
at exact figures: passages differing only by fiscal year are near-identical, so
a question about FY2023 happily retrieves FY2022. Numbers therefore come from
SQL, where `FY2023` is an exact match. Narrative comes from BM25.

BM25 rather than embeddings: financial queries are keyword-heavy, it needs no
key and no model download, and it keeps digits as tokens — `2025` and `416` are
the most discriminating terms in this corpus.

## 3. Access — the differentiator

**`src/access/`** — four small modules, and the only path to any data.

```
model.py   Tag · Role · Decision           the vocabulary
gate.py    AccessGate                      the single read choke point
guard.py   QueryPlan · guard_plan()        the derivation guard
audit.py   audit() · read_audit()          append-only decision log
```

### The gate

Two enforcement surfaces, because there are two stores. **Both filter before
retrieval, never after.**

| Store | Mechanism |
|---|---|
| `facts.db` | `sql_predicate()` returns a parameterised `WHERE` fragment bound into the query — restricted rows are never selected |
| BM25 index | `filter_chunks()` runs before scoring — a restricted chunk never competes for a slot |

Post-retrieval filtering would still leak through **result counts and response
latency**, both observable.

The gate deliberately does not know what a `Chunk` or a `Fact` is. It requires
only `.tag`, `.fiscal_year` and `.quarantined`, so the access layer imports
nothing from the layers above it.

### The guard

The hardest clause in the brief is leakage *"when the answer would require
combining restricted and permitted sources"*.

The agent emits a `QueryPlan` — intent, metrics, periods, tags — **before
anything is fetched**. `guard_plan()` validates it in plain Python. The model
writes the plan; it gets no vote on the verdict.

Refusal is all-or-nothing, because executing the permitted half of a mixed plan
is exactly what leaks. Every violation is collected rather than returning on the
first, so a role restricted on two dimensions is told about both.

### The audit log

Every decision, allow **and** deny. A log containing only refusals cannot answer
"what did this role actually read", which is the first question an auditor asks.

It records the decision and never the content: timestamp, role, a short context
label, verdict, reason, denied tags and periods. **No document text, no prompt,
no answer body.** It is the file most likely to be shared while debugging, and
it must not become a second unguarded copy of the data the gate protects.

## 4. Agent

**`src/agent/`**

| Module | Responsibility |
|---|---|
| `planner.py` | question → `QueryPlan`, using `metric_tags.json` and config aliases |
| `guard` (in access) | approve or refuse the plan |
| `tools.py` | the four scoped tools, each taking `gate` as a required argument |
| `loop.py` | plan → guard → fetch → compose → audit |
| `llm.py` | provider adapter; returns `None` rather than raising |
| `sanitize.py` | prompt-injection detection |

**RBAC lives inside each tool, not around it.** The gate is a required keyword
argument of all four, so enforcement holds identically whether the caller is the
agent loop, the CLI, the web API, or a test. Telling an agent not to read
something is a request; not giving it a tool that can is a guarantee.

Every tool returns the same envelope — `{allowed, reason, rows}` — and never
raises on a denial, because an exception collapses "you may not see this" into
"there is no such data" the moment something upstream catches it.

Two planner properties that carry weight:

- **Tags come from configuration, never from the question.** If a question could
  influence its own tags, a request could under-declare and walk past the guard.
- **An unknown metric is treated as maximally restricted.** Failing open on an
  unrecognised name is how a typo becomes a bypass.

## 5. Feedback

**`src/feedback/`** — two mechanisms, deliberately different in kind.

- **Re-ranking** changes *what the model is shown*: chunks in down-voted answers
  are demoted, up-voted ones promoted, compounding across repeats.
- **Correction memory** changes *how it reads*: a correction written against a
  similar question is injected as `<user_correction>`, labelled and placed last
  so it cannot be mistaken for something read out of a filing.

Both are scoped by question similarity (token overlap, threshold 0.3). Applying
feedback globally would make the system get worse the more it is used.

**The security property:** feedback runs strictly *after* the gate, on a list
from which restricted material has already been removed. Twenty up-votes on a
compensation chunk neither unlock a refusal nor surface that chunk in a
permitted query — the guard has already decided, before feedback is consulted.

## 6. Prompt injection

**`src/agent/sanitize.py`** — four layers, and the weakest is named as weak.

| Layer | Strength |
|---|---|
| Quarantine at ingest — flagged passages are dropped by the gate for **every** role | structural: the text never arrives |
| No text-to-execution path — parameterised SQL, typed tool arguments | absolute |
| Delimiting and labelling in the system prompt | mitigation |
| Output checking against known restricted terms | mitigation, weakest |

Patterns target **manoeuvres** rather than wordings — overriding instructions,
asserting a system turn, claiming authority, demanding disclosure — so
paraphrases are still caught. Text is whitespace-normalised first, because PDF
extraction breaks words across lines and an attacker gets that free with a
narrow column.

Quarantine is a *safety* rule, not a permission. Giving CEO an override would
read like seniority and behave like a vulnerability.

---

## 7. Interfaces

Both are thin. Neither holds access logic — each builds an `AccessGate` from the
asserted role and calls the same `answer()`. Two enforcement points would mean
two things to keep in agreement, and the one that drifts is the one that leaks.

- **`src/cli.py`** — one-shot (`--ask`) or interactive, with `:up`, `:down`,
  `:correct` to drive the feedback loop live. Exits `3` on refusal so the
  outcome is assertable from outside the process.
- **`src/api.py` + `src/web/index.html`** — the console. Its primary object is
  the *decision*: a five-stage pipeline where a refusal is visible as a stopped
  pipeline rather than a sentence claiming something was blocked.

## Module dependency direction

```
access/     ←── understanding/  ←── ingest/
   ▲                 ▲                ▲
   └───────── agent/ ┘                │
                ▲                     │
        feedback/                     │
                ▲                     │
        cli.py / api.py ──────────────┘
```

`access/` depends on nothing but the standard library and PyYAML. That is
deliberate: it is the module that must stay readable on one screen, and the one
whose correctness everything else assumes.
